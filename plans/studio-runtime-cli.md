# Remote Studio/runtime CLI: inventory and first slice

Status: **first thin REST client implemented**, 2026-09-17, at
[`clients/agent-cli`](../clients/agent-cli/README.md). No backend API, authentication
policy, production deployment or live credential changes were made for the CLI.
Later features below remain proposals, not shipped functionality.

## What exists

- Runtime Django management commands in
  `packages/python/django_agent_runtime/management/commands/`: workers, ASGI development
  server, agent-system import/export, knowledge indexing and maintenance. These
  require a configured server environment; they are not remote HTTP clients.
- Studio's `run_eval_suite` management command is likewise host-local.
- Runtime ACP server/client and remote project/session targeting support remote
  **agent execution**, not general remote Studio administration.
- `clients/agent-frontend/packages/agent-client` supplies a TypeScript chat client,
  not a Studio administration executable. Warp's CLI targets a different product.
- The broader checkout inventory confirmed **Warp's Go remote-admin CLI** at
  `products/warp/cli`, **Parrot's Python registry CLI** at `products/parrot/parrot-cli`, and **Jimmy's
  local coding-agent CLI** at `products/jimmy`. None supplies general runtime/Studio REST
  administration. Their product-specific APIs/auth were not copied into this CLI.
- No existing suitable Studio/runtime console client was found; this CLI is new.

## Verified API/auth foundations

The local host mounts runtime at `/api/agent-runtime/` and Studio at `/studio/`.
Other installations may use different mounts: do not hard-code them in the client.

| Surface | Existing foundation | Boundary |
| --- | --- | --- |
| Studio workspace | `/studio/api/workspace/projects/`, `threads/` and related routes | `WorkspaceView` explicitly supports **SessionAuthentication and TokenAuthentication**, requires an active user, and applies workspace ACLs. |
| Runtime | `/api/agent-runtime/agents/`, `runs/`, `conversations/`, run event/stream routes | Inspect endpoint and host permission policy; do not treat a successful list as administrative authority. |
| Current host identity | `/api/accounts/profile/` | Host-specific, not a portable runtime/Studio identity contract. |
| M0 tracker | `/sdlc/api/scopes/` and scoped item/note routes | Django session authentication plus CSRF only; it does **not** currently accept a DRF token. |

DRF TokenAuthentication uses the `Token` authorization scheme, not automatically
Bearer/JWT. A deployment may support other schemes. Authentication must not be
inferred from the TypeScript client's possible strategies alone.

The current host has allauth login and superuser MFA middleware. A password/token
endpoint's existence is not evidence that it enforces the same MFA policy. Review
issuance, revocation and service-principal policy before enabling remote CLI login.
Do not create a token-to-session bypass or exempt the tracker from CSRF to make
the CLI work. Stock DRF tokens are not scoped, short-lived CLI credentials.

Relevant code: Studio `api/workspace.py`, `api/workspace_urls.py`; runtime `urls.py`
and `api/views.py`; host `accounts/api/urls.py`, `agent_studio/middleware.py`;
SDLC `src/django_agent_sdlc/views.py`.

## Implemented ownership

Small independent HTTP client under **`clients/agent-cli`**. Executable name:
**`studio`** (renamed from `agentctl`), covering runtime with optional Studio API
commands. Distribution/import package `agentctl`, existing profile paths and
`AGENTCTL_*` environment variables remain unchanged; no executable alias is kept.
No Django dependency, settings imports, direct database access, SSH requirement or
dependency on Studio being installed. Python 3.11+ standard library only; zero
runtime dependencies. Packaging scaffold generated by uv with setuptools, built
offline in isolation; shared dependencies were not changed. No publication yet.

The server remains the authority for identity, authorization, defaults and writes.
Reuse existing services through their supported APIs; do not reproduce permission
logic or mutate saved backend configuration from a client-side convenience command.

## First deliverable: connect and inspect (implemented)

Available commands (the owning README is the usage reference):

| Command group | First-slice behavior |
| --- | --- |
| `studio profiles add/list/use` | Named installations, explicit origin and API mounts; store only non-secret profile metadata. |
| Credential input, not login/logout | Already provisioned host-approved credential through stdin, an external owner-only credential file or injected environment; no storage/issuance/browser-session borrowing. |
| `studio status` / `whoami` | Observe configured read endpoints; optional explicit host identity path. No claim of API-version discovery or an authorization grant. |
| `studio runtime agents list/get` | Existing runtime agent metadata API and host policy; agent detail uses a slug. |
| `studio studio projects list/get` / `studio studio threads list/get` | Existing workspace APIs and ACLs; configured Studio mount is `/studio/api/`, not `/studio/`. |
| `studio runtime runs list` | Safe metadata projection; no prompts, history, tool payloads or events in output. Run detail GET is excluded because the current server can schedule dispatch during retrieve. |

Provide table output plus stable `--json`, pagination, bounded timeouts and useful
exit codes. No writes, executions, migrations or shell operations in this slice.

### Discovery intentionally deferred

The user confirmed this should be a REST API wrapped in a CLI. **No new discovery
service or CLI backend is required for the first slice.** Explicit profiles name
the origin, API mounts and auth scheme; adapters use existing REST contracts.
If portable server discovery is useful later, add an optional authenticated
contract without breaking these older explicit profiles. Advertised capabilities
would describe availability, not authorization; requests still enforce permissions.

Support older hosts only through explicit mount/auth configuration and verified
endpoints. Unsupported capability discovery must not trigger anonymous fallback,
HTML/session scraping, automatic account creation or guessed write routes.

## Security and acceptance tests

- Credentials remain in an approved external source. The CLI never writes them;
  existing external files must be private and remain separate from profiles.
  Never put credentials in argv, URLs, config listing, errors or logs. Keychain
  integration and browser/device login remain future work.
- Require HTTPS remotely; permit HTTP only for explicitly local loopback profiles.
  Validate TLS; do not add a convenience certificate-verification bypass.
- Refuse cross-origin credential forwarding, redirects and pagination links;
  validate configured URLs without userinfo. Use authorization headers for SSE,
  not query-string tokens. Keep diagnostic output allowlisted.
- Test expired/revoked credentials, inactive users, MFA-required hosts, revoked
  memberships, guest projects, alternate mounts, unsupported capabilities, rate
  limits, pagination, timeout/cancellation and HTML/non-JSON error responses.
- Test both default paths and named exceptions. Prove read-only commands perform
  no writes and do not expose secrets even when a server response contains them.
- Run CLI unit/transport tests plus isolated server integration tests; no host DB
  in automated tests. Add a user-authorized remote smoke check after provisioning.

Implemented tests include real loopback HTTP command/output tests and actual
runtime/Studio API token/ACL/default-path contracts through an in-process HTTP
bridge. The bridge guards every read against SQL writes and runtime dispatch;
it is not a live-server test. MFA issuance and deployed-host acceptance are not
claimed; token-expiry semantics remain the host's responsibility.

## Subsequent slices

1. Explicit run start/watch/cancel using supported APIs, identity-bound streams,
   safe retry semantics and clear execution confirmation. No automatic retry of
   a non-idempotent run submission.
2. Scoped project/agent writes with server revision checks and explicit targets;
   never convert issue completion into delivery approval.
3. SDLC commands only after a deliberate non-browser authentication adapter and
   associated ACL/CSRF/default-path tests. Preserve current session support.

This work is independent of M1 delivery approvals and provider synchronization.
